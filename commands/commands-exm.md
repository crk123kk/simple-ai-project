# /plan

你是一位资深架构师。

请先不要写代码。

先分析需求并输出：

1. 功能拆解
2. 技术方案
3. 页面结构
4. 数据流
5. API设计
6. 数据库设计
7. 风险点
8. MVP最小实现
9. 后续扩展方向

要求：

- 优先简单可落地
- 优先MVP
- 避免过度设计
- 使用 markdown 输出

```
这个 command 的价值：

强制 AI 进入“架构思维”
而不是“代码补全模式”
```

# /review

你是一位 Staff Engineer。

请 review 当前代码：

重点检查：

1. TypeScript 类型安全
2. 潜在 bug
3. 性能问题
4. 可维护性
5. 重复逻辑
6. 安全问题
7. React 渲染问题
8. 边界条件
9. 错误处理
10. 是否符合最佳实践

输出格式：

## 问题

## 风险等级

## 修复建议

## 推荐代码

```

```

# /debug

请分析以下错误：

要求：

1. 根本原因
2. 调用链分析
3. 为什么会发生
4. 修复方案
5. 是否存在隐藏问题
6. 是否会影响其它模块
7. 如何避免再次发生

不要直接猜测。
请基于代码上下文分析。

# /refactor

目标：

1. 提高可维护性
2. 降低耦合
3. 提高复用性
4. 拆分大组件
5. 提高类型安全
6. 优化目录结构

要求：

- 不改变业务逻辑
- 不改变 API
- 保持行为一致
- 输出重构计划

# /architecture

请设计系统架构：

输出：

1. 总体架构图
2. 模块划分
3. 服务边界
4. 数据流
5. 缓存设计
6. 消息队列
7. AI模型调用链
8. 部署架构
9. 成本分析
10. 扩展性分析

要求：

- 优先低成本
- 优先MVP
- 支持未来扩展

# /task

请将需求拆解为：

1. 前端任务
2. 后端任务
3. AI任务
4. 数据库任务
5. 测试任务

每个任务包含：

- 描述
- 输入输出
- 依赖关系
- 优先级
- 工时估算

```
最经典的一类：Spec 驱动

这个其实是现在最先进的玩法。

例如：

PRD -> Tasks -> Architecture -> Implement
```
